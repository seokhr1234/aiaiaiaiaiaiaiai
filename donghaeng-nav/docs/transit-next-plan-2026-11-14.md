# 대중교통 우선 후속 실행 계획

작성: 2026-11-14 KST. 기준 커밋 `d0f5fad`, 작업 브랜치
`feature/gemini-route-selection`. [서울 확장 원계획](seoul-expansion-plan.md)을
대체하지 않고 현재 남은 작업의 실행 순서를 구체화한다.

사용자 지침: **대중교통부터 구현하며 UI 전체 최적화는 마지막에 수행한다.**
새 기능에 필요한 조작·접근성·모바일 동작은 매 단계 검사한다. 기존 화면 전체의
배치·버튼 디자인 개편을 대중교통 작업보다 먼저 진행하지 않는다.

## 현재 출발점

- 운영 배포·서울 기본 지도/등록 시설 검색·OSM 도보 참고 계산은 확인했다.
- ODsay 서버 어댑터, `/api/routes/transit`, 키 비노출·한도/실패 처리와 별도
  확장 화면의 참고 후보 모드는 있다. 운영 키 설정만 확인했으며 실제 검색은 미검증이다.
- 도보 구간·승차 시각 검증의 틀은 있지만 실제 시간표/역내/접근성 어댑터가 없다.
- 메인 화면의 대중교통 검색·노선/정류장/역·단계별 결과·지도 표시가 미완료다.
- 서울 전역의 휴식·휠체어·GPS 안내와 정밀 원본·현장 검증은 완료되지 않았다.

## T1~T3의 이번 구현 단위

1. 운영 `/api/transit/status`와 실제 검색을 확인한다. 자동 재시도·대량 시험을 하지
   않는다. 실제 요청 수와 성공/실패·검사일만 남긴다.
2. 실제 응답과 공식 문서의 필드로 정규화 계약을 보완하고 실패/결측/예산 제한을
   모의 검사한다. 키는 Vercel의 `ODSAY_API_KEY`에서 서버만 읽는다.
3. 메인 화면에서 별도 페이지 이동 없이 대중교통 참고 후보를 조회한다. 상태 문장은
   자동 해석하며 조건 체크박스나 AI 실행 버튼을 추가하지 않는다. 업체로 좌표를
   보내는 사실을 검색 전에 설명한다.
4. 후보는 참고용으로 표시하고 계단 회피/휠체어/휴식·환승 시각이 검증되지 않았음을
   구분한다. 임의로 최적/조건 충족/승강기 정상·앉을 수 있음/GPS 안내 가능이라 하지 않는다.
5. 후보 간 선택, 노선/승하차·환승 순서, 확인된 좌표만 지도에 표시한다. 지도 기하가
   없으면 선을 추측하지 않는다. 상세 기하 API는 계약/권한·추가 호출 예산 확인 후 연결한다.
6. 정상·빈 결과·손상·API 실패/한도·취소·늦은 응답·입력 변경·320/393px·키보드·
   기존 월곡/서울 도보 회귀를 검사한다. 코드/자료 무결성 재검증 후 HTML 5개도 갱신한다.

## 마지막 UI 최적화에서 해결할 항목

- 지도 위 시설/정밀/확대 버튼·출처/상태 안내·팝업·하단 패널이 서로 가려지는 경우.
- 모바일 상단/하단 고정 영역과 키보드·주소창·안전 영역에 버튼/결과가 숨는 경우.
- 기존 디자인과 다른 과도한 사각형 버튼: 모서리·높이·간격·테두리·색·아이콘·
  글자 크기 및 활성/비활성/초점 상태를 공통 기준으로 정리.
- 긴 노선/정류장명·시간/요금 결측·다수 환승·빈/실패 결과의 줄바꿈과 스크롤.
- 터치 영역·키보드 초점/복귀·읽기 순서·명암·상태 읽기와 확대125~200% 확인.
- 320/393px·가로·데스크톱에서 실제 화면을 확인하고 기존 지도/GPS/저장/제보 회귀.

## 기록·게시 원칙

실제 소스는 `donghaeng-nav/dist/`이며 네이버 API는 사용하지 않는다. 기존 research와
원본 9개, 등록/추정/미확인 구분을 보존한다. 모든 변경은 최상위 수정이력에 추가한다.
기능 커밋·푸시·배포 후 실제 운영 화면/API까지 확인하고, main과 feature의 구조/커밋
차이를 다시 대조한 뒤 이력 보존 방식으로 반영한다. 배포 생략 표시는 사용하지 않는다.
