# 전체 여정 검토·로컬 교통 검색·실제 ODsay 연결

2026-11-14 KST · 기준 브랜치 `feature/gemini-route-selection`, `10ad62a` 이후 로컬 작업.
사용자 지시: 최종 이동약자 내비게이션 목표까지 구현을 이어가되 우선 API 없이
가능한 작업을 진행. 이후 사용자가 Server 키와 본인 IP 등록을 제공하여 실제
ODsay 연결까지 소량 확인했다. 키 값은 기록하지 않는다.

## 현재 실제로 되는 것

- 로컬 메인 화면에서 실제 ODsay 검색 성공: **25개 후보**, 화면에는 첫 5개를 표시한다.
  기존 키를 화면에 전달하지 않고 서버 메모리에만 연결했다. 초기 인증 확인 1회와
  메인 화면 확인 1회, 이번 실제 요청 **총 2회**다. 전체 업체 JSON/오류 원문은 저장하지 않았다.
- 실제 후보 선택 → 같은 조건의 서울 OSM 도보 재계산 → 전체 여정 확인을 연결했다.
  도보·승차·하차·환승 순서를 표시하고 각 구간의 출입구·시각·접근성 미확인을 구분한다.
- 구간별 확인 목록은 정류장/출입구, 역내 연결, 계단 없는 접속, 휠체어 공간,
  해당 운행편 저상 여부, 노면 경사, 반복 휴식 등 사용자 조건에 따라 달라진다.
- 전체 여정 수동 확인과 모의 재생, 이전/다음·일시정지·종료를 제공한다. 후보나
  입력 변경·화면 종료 시 타이머/지도 표식을 정리한다. 차량의 가짜 직선 경로를
  그리지 않으며 재생 위치를 실제 GPS 위치로 표시하지 않는다.
- 서울 도보 결과에도 같은 검토/재생 조작을 연결했다. 기존 월곡 상세 GPS·저장·시설
  제어는 유지한다. 서울 참고 경로/미검증 혼합 여정을 실제 GPS 길 안내로 승격하지 않는다.

## API 없이 구현한 부분

### 로컬 파일의 교통 후보 검색

`services/transit/local-network.mjs`와 `provider.mjs`는 파일의 정류장·노선·명시 운행일
시간표에서 최대 승차 3구간/환승 2회, 참고 후보 최대 5개를 계산한다. 출발/도착
800m 이내 가까운 정류장 각 최대 3곳의 도보는 같은 사용자 조건으로 기존 도로망에서
계산한다. 도보가 계산되지 않으면 조건을 풀거나 직선 거리를 보행 시간으로 만들지 않는다.

출발 도보 뒤 놓친 편, 다음 편, 자정 이후 24시 표기와 명시된 운행일을 처리한다.
같은 ID 환승도 실제 역내 접속이 검증됐다는 뜻은 아니다. 없는 휴일/다음 날 편을
만들지 않으며 지연/운휴/운행 완전성을 추정하지 않는다. 12초 계산 예산·승차 3구간·
확장 상태 2만·동시 검색 1개 제한을 둔다. 이 선택적 모드는 외부 API로 폴백하지 않는다.

**실제 서울 정류장·노선·운행일 시간표 팩은 새로 확보하지 않았다.** 검색 검사의
자료는 합성 fixture이며, 자료가 없으면 `local_data_missing`으로 표시한다. 기존에
내장된 시설·도로 자료만으로 버스 운행편을 만들어내지 않는다.

서버 실행 예:

```sh
DONGHAENG_TRANSIT_MODE=local DONGHAENG_TRANSIT_PACK=/absolute/path/to/transit-pack.json node server.mjs
```

팩 스키마는 `donghaeng-transit-pack-v1`이다. `stops`는 `id/name/ll`, `lines`는
`id/name/mode`, `timetable`은 이전 [시간표 파일 계약](transit-timing-review-2026-11-14.md)을
사용한다. 이제 `timetable.idNamespace`를 명시할 수 있으며 각 trip의 같은 namespace와
맞아야 한다. ODsay 또는 기관 고유/자체 ID 체계의 실제 일관된 대응을 사용할 수 있다.
다른 namespace의 동일 숫자 ID는 같은 지점으로 간주하지 않는다.

파일 경로는 서버 환경에서만 설정한다. 브라우저 입력으로 임의 파일/URL·검증 주장을
받지 않는다. 최대 16MiB의 JSON만 읽으며 파일/파싱 오류 원문을 클라이언트에 노출하지 않는다.
Node와 Vercel 진입점 모두 같은 공급자 선택 계약을 쓴다. Vercel에서 쓰려면 해당 파일도
실제 배포 함수에 포함되어야 하며, 이번에 그 운영 자료를 배포한 것은 아니다.

### 접근성·반복 휴식

`evidence.mjs`는 서버 소유 기록의 namespace/노선/양쪽 정류장 ID·출처·관측/만료를
검사한다. 저상/휠체어 공간은 특정 `tripId`와 맞아야 하며, 경사는 기록의 `maxSlope`가
요청 상한을 충족해야 한다. 상충하는 유효 자료 중 통행 불가 근거를 지우지 않는다.

반복 휴식은 해당 경로 버전에 결속된 접속 확인·이용 적격 장소만 인정한다. 이동/대기/
승차를 포함한 연속 시간과 각 휴식 체류, 도착부터 휴식 종료까지의 자료 유효기간,
벤치/쉼터 종류·반복 간격을 검사한다. 차량 탑승을 휴식 완료로 간주하지 않는다.
시간이나 접속 자료가 부족하면 미확인이다. 현재 실제 서울 자료의 시간·출입구가
검증되지 않아 휴식 요청을 자동 충족시키지 않는다.

선택적 팩의 `accessEvidence`/`restOpportunities`는 `configured-review.mjs`를 통해
참고 여정 검사에 연결한다. 현재 도보는 계속 미검증이므로 실시간 길 안내/AI 추천
적격으로 승격되지 않는다. 이 구현은 필요한 자료를 제공할 수 있는 검증 기반이며,
실제 저상차량·승강기·반복 휴식 장소를 확보했다는 주장이 아니다.

## 현재 실행과 남은 작업

로컬 서버 `http://127.0.0.1:4187`에 키를 메모리로만 연결해 실행 중이다. 서버 종료 시
키는 재설정해야 하며, 로컬 Server 키/IP 인증 성공이 Vercel 호출 IP의 성공을 뜻하지 않는다.
Vercel 환경변수·출구 IP/인증과 운영 배포 확인은 별도다. 사용자 대화대로 커밋은
서원석이 할 수 있도록 변경 패치를 준비하며 이번에 푸시/배포하지 않는다.

- T1: 로컬 실제 인증/검색 성공. Vercel에서 같은 키로 성공하는지는 미확인.
- T4: 실제 출입구/보도 편/층위·기관 ID 대응 및 접근성 보행 자료 부족.
- T5: 정적 시간표 파일 처리와 여정 검사 구현. 실제 자료·휴일/지연/막차 운영 연결 미완료.
- T6: 요구별 접근성·반복 휴식 검증 코드 구현. 실제 운행편/승강기·현장 근거 미확보.
- T7~T9: 원계획의 정밀/GIS·주소 검색·성능/운영·Android/iPhone 현장 검증 미완료.
- T10: 새 조작의 모바일/키보드와 정리 동작은 검사했으나 전역 UI 최적화는 후순위 유지.

따라서 **전체 최종 제품/서울 휠체어 실시간 길 안내 완성으로 표시하지 않는다.**
현재는 실제 교통 후보와 도보 참고 계산, 구간별 검토/수동·모의 이동을 연결한 상태다.
